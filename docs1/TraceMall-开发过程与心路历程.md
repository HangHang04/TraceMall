# TraceMall 开发过程与心路历程

## 1. 我为什么要做这个项目

一开始我并不想把 TraceMall 只做成一个普通水果商城。单纯的商品列表、购物车、订单，其实很容易落入“功能都能点，但项目没有记忆点”的问题。  
我更想做的是一条完整链路：用户能买水果，商家能生成批次二维码，消费者能扫码验真，监管方还能看到异常告警。这样项目才不只是 CRUD，而是一个“交易 + 溯源 + 风控 + 监管”联动的系统。

所以我从最开始就给自己定了一个方向：

- 商城功能要能跑通；
- 溯源数据不能只是展示，要能查到事件链；
- 二维码不能只是图片，要和验真规则真正联动；
- 监管页面不能只是表格，要能看到风险结果沉淀。

## 2. 我是怎么一步一步做下来的

### 第一阶段：先把工程骨架跑起来

我先把项目分成前后端两个目录：

- `web/`：Vue 3 + Vite，负责前端页面和交互；
- `server/`：Spring Boot，负责业务接口、验真逻辑和数据库访问。

这样做的原因很简单，前端和后端职责清晰，后面无论是做答辩演示还是继续扩展，都会更好维护。

前端先把这些基础能力接好：

- 路由切换；
- Pinia 登录态管理；
- Axios 请求封装；
- 消费者、商家、监管方三个角色页面。

后端先把这些基础能力搭起来：

- 登录认证；
- 商品与订单接口；
- 批次与溯源事件接口；
- 二维码验真接口；
- 风险告警与审计日志接口。

### 第二阶段：把“溯源”从展示概念变成真正的数据链路

如果只做一个“商品详情页 + 溯源时间线”，其实还不够，因为那只是把数据库内容打印出来。  
我真正想做的是让溯源信息具备“可信校验”的味道，所以后端设计成了：

- 链下保存完整业务明细；
- 关键事件生成哈希；
- 通过锚点网关模拟上链校验；
- 二维码里带 `traceId` 和签名；
- 消费者扫码后，系统进行格式、签名、锚点、频次和地理异常的联合校验。

这样一来，二维码就不再只是“跳转链接”，而是可信链路的入口。

### 第三阶段：我开始意识到，页面不能只是“能用”

最开始的前端虽然功能基本齐，但页面观感偏“后台表单堆叠”，用户路径也比较散。  
我后来决定不再做局部修补，而是直接重构界面结构：

- 消费者首页改成“商城入口 + 快速验真 + 摄像头扫码 + 商品推荐”的组合布局；
- 商品详情页同时展示商品信息、批次摘要、溯源事件链和二维码；
- 商家端除了表单，还增加了二维码生成展示；
- 监管端加入了概览指标和趋势图；
- 登录页重新设计成多角色系统入口，而不是单纯一个表单。

我希望用户一进入系统，就能看懂这个项目和普通商城的差异到底在哪里。

## 3. 这次开发中真正遇到的一个困难

### 困难点：二维码“能扫”不代表“能验”

最开始我考虑过一种简单方案：二维码里只放 `traceId`。  
这样做的优点是实现快，扫码也容易，但很快我发现一个实际问题：

- 后端验真接口不仅需要 `traceId`，还需要 `signature`；
- 如果二维码只有 `traceId`，消费者扫码后还得手动补签名，体验非常差；
- 如果前端只做“扫出来就展示”，那这个二维码并没有真正和验真逻辑闭环。

也就是说，**扫码成功** 和 **验真成功** 是两回事。

### 我最后的解决方法

我把二维码内容统一改成了“公共验真链接”：

- 链接中携带 `traceId`；
- 同时携带 `signature`；
- 扫码后进入公共溯源页 `/trace/scan`；
- 页面自动回填参数并直接调用验真接口；
- 同时我又保留了兼容能力，支持解析纯文本 `TRACE-XXXX` 和 JSON 二维码内容。

这样做带来了几个直接收益：

- 商家生成二维码后可以直接下载分发；
- 消费者扫码后无需登录，也无需手填参数；
- 前端扫码、后端验真、溯源详情三者真正打通；
- 演示时非常顺，打开摄像头扫一下就能看到结果。

这个问题让我意识到，做系统不能只关注“功能点有没有”，还要关注“链路是否闭环”。

## 4. 过程中我做过的一些取舍

### 取舍 1：先用 Mock 锚点，而不是一开始就强接真实链

如果一上来就接完整区块链环境，工程复杂度会迅速上升，项目节奏也会被拖慢。  
所以我选择先把“哈希生成、锚点校验、结果回传”的接口抽象出来，底层先用 Mock 网关跑通。

这个取舍的价值在于：

- 演示链路先成立；
- 论文中也能说明“业务明细链下、关键摘要链上”的设计思想；
- 后续如果真要接 Fabric 或其他链，只需要替换网关层。

### 取舍 2：前端扫码选用成熟库，不自己造轮子

二维码识别如果自己手写，兼容性和调试成本会很高。  
所以我直接接入成熟的扫码库，前端主要负责做三件事：

- 摄像头启动与停止；
- 扫码结果解析；
- 与验真表单和后端接口联动。

我认为这是更工程化的做法，把时间花在真正体现项目价值的地方，而不是重复造基础轮子。

## 5. 做完之后，我对这个项目的理解

现在再回头看，TraceMall 对我来说已经不是一个“水果商城毕设”，而是一个围绕可信流通展开的系统原型。

它最有意思的点不是某一个页面，而是这些角色和能力能串起来：

- 消费者买水果；
- 商家生成批次二维码；
- 消费者扫码验真；
- 监管方看到异常沉淀为告警。

这种闭环感，是我最满意的地方。

## 6. 如果我继续往下做

如果后面继续做，我会优先推进下面几件事：

1. 增加真实图片、物流轨迹和温湿度等更细的溯源字段；
2. 引入真实地图位置和更细的风控规则；
3. 把监管告警做成可处理、可闭环的工单流程；
4. 尝试把锚点网关替换成真实区块链接口；
5. 增加性能、安全和异常注入测试，为论文实验部分提供更扎实的数据。

## 7. 最后总结

这次开发给我的最大感受是：

一个项目真正有说服力，不在于页面有多少，也不在于接口有多少，而在于它是否围绕一个核心问题做到了前后贯通。  
TraceMall 的核心问题就是“水果来源是否可信、消费者是否能验证、监管是否能介入”，而我这次的开发重点，始终都围绕这个目标在推进。
